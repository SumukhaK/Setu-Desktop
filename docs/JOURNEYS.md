# Setu user journeys

This is the canonical journey specification for [Setu Desktop](https://github.com/SumukhaK/Setu-Desktop) and [Setu Android](https://github.com/SumukhaK/Setu-mobile). The baseline is Setu SDK **v1.1.0** at [921aded](https://github.com/SumukhaK/Setu/commit/921aded), specified by its [API_SPEC.md](https://github.com/SumukhaK/Setu/blob/v1.1.0/API_SPEC.md). The HTML wireframes use deterministic fixtures. Rows marked **SDK binding** name the v1.1.0 method, event or Kotlin API a screen uses. Rows marked **Integration** describe application work. Rows marked **SDK or service gap** need a capability that v1.1.0 does not provide. The ordered implementation tickets are in [TDD_TICKETS.md](TDD_TICKETS.md).

**Version skew.** A v1.1 desktop talking to a v1.0 phone agent falls back to v1.0 behaviour. New features answer `-32024 unsupported` (`ErrUnsupported`), and the phone sends no session or `peer_closed` events. Show **Update Setu on the phone to use this feature**, never a generic error.

## J1 · Choose a workspace

- **Solo.** Both apps start locally without an account. On Android, start hosting after readiness checks. On desktop, pair by code or select a locally paired device. The code has four digits, a hyphen, and six digits (`NNNN-NNNNNN`). Accept ten digits and format after the fourth digit, preserving leading zeroes. Validate pasted text. The phone rotates its code after successful pairing or three failed PAKE attempts that reach the phone. A stale code prompts the developer to read the current code on the phone. Successful pairing automatically pins both sides. Pins are permanent on the phone in v1.1.0. **SDK or service gap:** there is no phone-side trusted-desktop list or revoke. [Device agent](https://github.com/SumukhaK/Setu/blob/v1.1.0/core/internal/engine/device.go) · [Desktop pairing](https://github.com/SumukhaK/Setu/blob/v1.1.0/core/internal/engine/connect.go)
- **Corporate desktop.** Show the organization's configuration and an SSO action. **Integration.** The app opens the system browser for OIDC with Authorization Code and PKCE. After verified organization sign-in, the organization's token service returns a Setu-compatible EdDSA JWT bound to the daemon's public key through `cnf.key`. `identity.public_key` reads the SDK identity and does not issue a token. The shipped identity uses a local file-backed Ed25519 key. A hardware-backed signer and custody guarantee require an adapter or SDK change. Corporate access also depends on enrollment, relay policy, and device grants. Keep OIDC tokens, Setu JWTs, and the daemon IPC secret separate.
- **Corporate Android.** EMM supplies `relay_url`, `enroll_token`, `policy_json`, and an optional `relay_pin`. Push the per-device policy from `setu policy scope` or relay `GET /v1/policy?device=<id>`; since v1.1.0 the SDK also scopes any policy it receives to this device's grants, and the app must not cache the unscoped JSON. When an enrollment token first arrives, show **Your organization now manages this device** once per enrollment. Then show **Waiting for IT policy configuration** for `ConnectionState.PolicyMissing`, or the restricted screen for `ConnectionState.Blocked`. No pairing code is available in Corporate (`pair()` throws `PairingUnavailable`). **Integration.** Treat known enterprise provisioning with incomplete settings as Corporate and fail closed. Apply restrictions on a configuration change before starting or restarting the agent. Isolate cached Solo state from managed hosting and do not fall back to a Solo relay. Desktop mode guidance is informational. The managed Android host and corporate relay enforce policy. [API_SPEC §4.2 and §5.3](https://github.com/SumukhaK/Setu/blob/v1.1.0/API_SPEC.md#42-models)

## J2 · Prepare the phone

| Condition | Guide and readiness gate | Recovery |
| --- | --- | --- |
| Android 11+ on Wi-Fi | Enable Developer options, then Wireless debugging. Pair the developer computer's ADB key once through Setu (below), then attach through the debugging connection endpoint. | If Android's pairing dialog closes or its port changes, reopen it and use the new values. Help the tester find **Build number** or the OEM equivalent. Recheck on returning from Settings. |
| Android 10 or cellular-only | On an approved device and trusted setup network, authorize USB debugging on a locally connected computer, then use `adb tcpip 5555` over USB. Verify the phone-side endpoint (`ConnectionState.Online.adbdEndpoint` is `127.0.0.1:5555`) and relay reachability before unplugging. Use Setu's encrypted relay for remote access. Android may separately ask to authorize the developer's ADB key on the phone. | Recheck following reboot, an adbd restart, or an OEM setting change. If the device cannot support the fallback, stop and contact IT or use supported Wi-Fi. Legacy adbd may listen on network interfaces. Avoid public exposure, forwarding port 5555, or using untrusted networks. Stop the host and restore USB debugging mode when the authorized task ends. |
| Android 13+ | Check `POST_NOTIFICATIONS` and explain the foreground notification before asking. Denial can leave foreground hosting running, with a reduced notification experience and an in-app **Stop hosting** action. | Offer **Open notification settings** and recheck. Build the notification wording with `SetuNotifications.content(state, sessions)`, but post **`publicText` in both the private and public versions** and use `VISIBILITY_SECRET`. Never post `text`, which may contain the pairing code. This is stricter than the SDK §4.4 example on purpose: the code appears only inside the app. |
| Battery and OEM policies | Check `PowerManager.isIgnoringBatteryOptimizations` and offer system battery settings. Xiaomi MIUI/HyperOS uses Autostart and battery **No restrictions** where available. Samsung uses **Never sleeping apps**. ColorOS can expose per-app auto-launch and background activity. Resolve known vendor destinations before opening them and fall back to system app settings and manual instructions. | Treat OEM switches that cannot be read programmatically as unknown or tester-confirmed. If MIUI returns `INSTALL_FAILED_USER_RESTRICTED`, explain **Install via USB** and **USB debugging (Security settings)** where present and approved by IT. This is install recovery, separate from host readiness. |

**SDK binding · Android 11+ debugger pairing.** On the phone, the tester opens *Wireless debugging → Pair device with pairing code*, which shows a six-digit code and a port. On the desktop, the developer enters the code; the port is optional. The desktop calls `session.pair_adb {device_id, pairing_code, pairing_port?, timeout_ms?}`. `pairing_port` 0 or absent asks the phone to discover its own `_adb-tls-pairing._tcp` service. The code is passed only to the local `adb pair` and travels inside adb's SPAKE2 exchange, which the tunnel also encrypts. Result: `{device_id, paired, transport, output?}`. Errors: `-32023 adb_pair_failed` (wrong code, dialog closed or wrong port: keep the form and ask for a fresh code) and `-32024 unsupported` (phone runs a v1.0 agent). An `adb_pair` event reports the outcome. The daemon's `--adb PATH` selects adb. Treat the code as an ephemeral input and omit it from logs, diagnostics, crash reports, persisted state and notifications. The Android app never asks for the system code. Keep the automated flow behind a flag until the device-lab run passes. [API_SPEC §1.1 PairADB, §2.1](https://github.com/SumukhaK/Setu/blob/v1.1.0/API_SPEC.md#11-setuclient) · [AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/docs/dev/adb_wifi.md) · [Android USB troubleshooting](https://developer.android.com/studio/run/device) · [Notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission) · [Lock-screen visibility](https://developer.android.com/reference/android/app/Notification#VISIBILITY_SECRET) · [Battery allowlist](https://developer.android.com/reference/android/os/PowerManager#isIgnoringBatteryOptimizations(java.lang.String))

## J3 · Select a device and attach ADB

1. **Solo:** select a paired device from `devices.list`; presence is unknown. **Corporate:** list the user's granted devices from `devices.presence` → `{devices: [{device_id, online, connected_at?, transport?, sessions}]}`. Revoked devices are reported offline. Poll every 30 seconds, on window focus and on `events.dropped`. Data from a poll under 60 seconds old is fresh; anything older shows **Last seen unknown**. Show the exact `device_id` with an optional local nickname. `devices.presence.transport` is how the phone reaches the relay, not the session's path, so never show it as the session path. [API_SPEC §5.2](https://github.com/SumukhaK/Setu/blob/v1.1.0/API_SPEC.md#52-presence-for-users-110)
2. Desktop calls `session.connect` with a pairing code in Solo for first contact, or with the saved or granted `device_id`. The UI can cancel a pending connect with `session.cancel {request_id}`, which answers the connect with `-32022 cancelled`. Display the returned `adb_addr` on loopback. **Tunnel ready** identifies the authenticated preflight and local listener. Show the path from the latest `path_up` or `path_down` `transport` for the session's tunnel. Before any path event, use the audit `session_start.transport` record when audit is on (always in Corporate). Otherwise show **Path unknown**. **SDK or service gap:** the desktop does not learn the initial transport in Solo until a path event; `session_up` carries no `transport`. Preserve reported relay TCP or WS labels. The status strip omits RTT and geographic location.
3. **Integration.** **Connect ADB** runs local Platform Tools against that exact loopback endpoint, then observes `adb devices` (or `host:track-devices-l`) for its serial. Only `device` confirms **ADB attached**. `unauthorized` directs the user to phone authorization and `offline` prompts a retry. Keep listener readiness visible independently. Missing Platform Tools leads to Diagnostics. After attachment, Android Studio's device picker can choose that transport. [ADB CLI](https://developer.android.com/tools/adb)
4. On Android, `ConnectionState.Online` reports hosting, the device ID, the optional adbd endpoint or warning, and `path`. **SDK binding:** `SetuManager.sessions: StateFlow<List<DeviceSession>>` lists the desktops connected now: `id`, `peerLabel`, `transport`, `kind` (`adb` or `adb-pair`), `openedAtMs` and `path` (`UP`, `DOWN`, `LOST`). Each row has **End**, which calls `endSession(id)`; the desktop's session then ends with `-32026 peer_closed` and is not retried. Visible **Stop hosting** stops the whole agent and clears the list. `adbd_unreachable` prompts the user to restore the selected debugging method. **SDK or service gap:** `peerLabel` prefers the name the desktop sends about itself over the verified corporate user, so show it as **Computer name (unverified)** until the SDK exposes a verified subject. No approval dialog in the v1.1.0 flow. [API_SPEC §4.1](https://github.com/SumukhaK/Setu/blob/v1.1.0/API_SPEC.md#41-setumanager)
5. **Desktop label.** The desktop starts its daemon with `--label "<computer name>"` (user-editable, default hostname). Without it the phone shows `desktop-<8 hex>`.

## J4 · Recover from corporate denials

| Signal | Screen and recovery |
| --- | --- |
| `-32017` · No grant | **You don't have access to this device.** Request a grant from the IT administrator. Keep the device ID available to copy. |
| `-32018` · MDM blocked | **Debugging is restricted by your organization's device policy.** Contact IT. The Android host exposes `ConnectionState.Blocked`. Use the explicit status when supplied and keep generic denials generic. |
| `-32014` · Access revoked | **Your access was revoked by your administrator.** End the affected access state and stop automatic retries. Since v1.1.0 the relay persists revocations across restarts. |
| `-32015` · Invalid token or `-32016` · Expired token | Sign in via SSO to recover. For expiry, say **Your corporate session expired. Sign in via SSO to resume.** **SDK binding:** the token refresher writes the new Setu JWT atomically to the workspace's `--identity-file`, which the daemon watches every 2 seconds, or the app calls `auth.set_token {token}` → `{subject, token_id?, expires_at}`. Live sessions keep running and nothing restarts. Watch for `token_updated`, and for an `error` event when a written token is rejected (the old token stays). A token for a different `subject` is rejected while sessions are live: show **Signed in as a different user. End current sessions to switch.** |
| `-32025` · Session expired / `session_expired` event | **Your organization's session time limit was reached.** One-click **Reconnect** runs a fresh `session.connect`, which re-authenticates. No automatic retry. |
| `-32026` · Peer closed / `peer_closed` event | **The session was ended on the phone.** Show `peer_reason` if present. No automatic retry; **Reconnect** is manual. |
| `-32022` · Cancelled | Silent. The user cancelled; return to the previous screen. |
| `-32024` · Unsupported | **Update Setu on the phone to use this feature.** |
| `-32027` · Busy | Internal. Back off and retry once; never shown to the user. |
| Policy time cap | The relay and both endpoints enforce `max_session_seconds` as a hard cap counted from the tunnel handshake. Rejoins do not extend it. **SDK or service gap:** no authoritative deadline is exposed (`SessionInfo` has no `expires_at`, and the phone may hold a lower per-device cap), so show no countdown or advance warning. |

[API_SPEC §2.3 errors](https://github.com/SumukhaK/Setu/blob/v1.1.0/API_SPEC.md#23-errors) · [§5.3 session cap](https://github.com/SumukhaK/Setu/blob/v1.1.0/API_SPEC.md#53-session-cap-and-per-device-policy-110)

## J5 · Background, reconnect and stop

- **Daemon lifecycle.** The desktop starts `setu-daemon --listen 127.0.0.1:0 --state <workspace dir> --label <name> …` and reads the single `daemon_ready` JSON line from stdout (`listen`, `version`, `token_file`, `pid`). It authenticates each connection with the token from `token_file`, keeps one events connection and one control connection, and uses unique request ids. Requests run concurrently (at most 128 in flight per connection). If a live daemon already owns the workspace's state directory, attach to it instead of starting a second writer. [API_SPEC §2](https://github.com/SumukhaK/Setu/blob/v1.1.0/API_SPEC.md#2-daemon-json-rpc-20-protocol)
- Minimize desktop to the system tray while keeping the daemon session alive. Relay's selected workspace and active session return on restore. **Quit** stops the daemon after confirming that live sessions will end. Android keeps hosting in a foreground service. Its notification can expose **Stop hosting** without disclosing credentials. Desktop **Disconnect** invokes `session.stop` for the selected session.
- **SDK binding · path events.** Bind `path_down {session_id, reason, transport}`, `path_up {session_id, transport, outage_ms}` and `path_lost {session_id, reason, outage_ms}`. `fields.session_id` is the 16-hex tunnel id; `event.session` is the client session (`s1`). A client session can carry several tunnels (one per adb TCP connection), so key state by tunnel and roll it up to the session. A tunnel emits at most one `path_down` per outage, then exactly one `path_up` or `path_lost`; a normal close emits none. For 0 to 10 seconds after `path_down`, show nothing. From 10 to 90 seconds, show a calm amber holding banner; say the debugger stays attached only while attachment is observable. On `path_up`, clear the banner and update the transport, which may switch (for example `relay-wss` to `lan`). On `path_lost`, say the phone is unreachable and ADB will need to reattach. The outer `retrying` and `session_down` events still apply. Clear stale banners on recovery, stop or terminal errors, ignore events for stopped sessions, and use a monotonic clock with no countdown. On Android, read each session's path from `sessions[].path`; `Online.path` holds only one path. `ConnectionState.Reconnecting` still means the agent process is restarting. [API_SPEC §1.5](https://github.com/SumukhaK/Setu/blob/v1.1.0/API_SPEC.md#15-events)
- On `events.dropped {count}`, resync with `session.list`, plus `devices.presence` in Corporate, before applying further events.
- In Solo, **Forget device** invokes `devices.forget` and deletes the local saved relationship. It does not remove the desktop key from the phone. For active access use **Disconnect**, **End** on the phone, or **Stop hosting**. In Corporate, the administrator revokes access via the relay (`POST /v1/revoke`, persisted). An application offering corporate sign-out must clear its own tokens and explicitly decide whether to end its sessions.

## J6 · Verify audit integrity and run diagnostics

- **This Computer's Audit Log.** Call `audit.verify` on entry. Show **Verified** when `valid` is true and `anchor=verified`. Show **Unverified** for a missing anchor, an absent verification key, a disabled log (`-32021`) or unavailable verification. Show **Tampered** when a returned chain fails verification or its anchor is invalid. Display warnings, broken record index and problem where the SDK returns them. Mark tampered exports accordingly if the report generator still allows export. Organization aggregation is handled by the central SIEM or webhook collector.
- Show **Operation-level** for visible classic ADB, **Session-level** for opaque Android ADB TLS, or unknown/mixed coverage if the source does not identify it. The relay transport and the Android ADB protocol are separate. **Export** calls `audit.report` for JSON, CSV or HTML with optional RFC 3339 date bounds. Save the generated report. The prototype previews these responses using fixtures. [API_SPEC §3](https://github.com/SumukhaK/Setu/blob/v1.1.0/API_SPEC.md#3-audit-record-and-report-schema)
- **Diagnostics.** Run the real `doctor` RPC and render status, detail and fix hint for `adb`, `state`, `paired_devices`, `proxy_env`, `relay_dns`, `relay_reach` and `audit_log`, including `relay` when relay checks are skipped. Allow unknown future checks. The `adb` check validates Platform Tools. Attachment still comes from the local ADB status adapter. Settings accepts **Custom relay URL**, **Relay certificate pin** and **Corporate HTTP proxy**. These are daemon start flags (`--relay`, `--relay-pin`, `--proxy`), so applying them restarts that workspace's daemon after a confirmation naming the live sessions it will end. The pin is the hex SHA-256 of the WSS leaf certificate DER, with optional colons. Standard TLS verification still applies. Explicit HTTP CONNECT proxy applies to WS/WSS. Redact proxy credentials in diagnostic output.

SDK-backed screens omit media capture, evidence uploads, inboxes, email/OTP, phone approval, manual code renewal, and a phone trusted-access editor. The pre-audit video remains a historical artifact.

## Implementation acceptance tests

Write these first against fakes for daemon RPC (`FakeDaemon`), local ADB (`FakeAdbServer`), the Android agent (`FakeAgentLauncher` feeding agent JSON lines into a real `SetuManager`), EMM policy, Android Settings and the monotonic clock. Run the behaviors that depend on Android or the relay against physical devices or controlled test relays before enabling those capabilities.
